# 文章の文体ルール（Blog と note）

佐藤竜也の文章の癖と構成のルール。次の 2 つの媒体の記事から読み取った。

- このサイトの Blog: `_posts/` の 2019〜2026 年の 128 本（特に Markdown で直接書いた 2021 年以降の 60 本）
- note（https://note.com/satoryu）: 2026 年 4〜9 月の 36 本（毎日書いていた 300〜1,300 文字の短い記事 30 本と、8 月以降の 3,000〜4,700 文字の長い記事 5 本）

生成 AI が「それらしい文章」を書くと外れやすい点を中心にまとめている。
第 1〜3 節と第 5〜7 節は両媒体に共通する癖、第 4 節は Blog の記事の型、第 9 節は note に固有の型。
Blog の記事を書くときは、textlint（`npm run lint`）に加えてこのルールに従うこと。

## 1. 一人称と読者への呼びかけ

- 一人称は **「自分」** を使う。「私」は改まった場面（転職報告、寄付の報告）でごく稀に使う程度。「ぼく」「僕」「俺」は使わない。Blog で「自分」216 回に対し「ぼく/僕」5 回、note でも「自分」162 回に対し「私」2 回、「ぼく」0 回。
  - 例: 「自分が積極的に最初に取り組んでいるデモのことについて話をしました」
  - 例（note）: 「自分は、チームを監視する人になろうとしていないだろうか。」
  - チームを指すときは「自分たち」。
- 一人称は多用しない。主語が自明な文では省く。1 記事に数回程度が目安。
- 読者は「方」「方々」で呼ぶ。「読者のみなさん」「皆様」とは言わない。
  - 例: 「もし要望やバグなどを見つけた方がおりましたら」「お祝いを贈ってやってもいいぞ！という DS な方向けに」

## 2. 文末と文体

- 文体は媒体で分ける。1 記事の中では混ぜない。
  - **Blog は基本ですます調**。ただし、手順やハマりどころを淡々と記録する技術メモ（コマンドや設定の話が中心の記事）は **である・だ調** で書くこともある
    - ですます: イベント参加報告、リリースのお知らせ、ふりかえり、読書、転職などの近況
    - である: 「SQL Server に ActiveRecord で複数レコードを INSERT するときのハマりどころ」「Mac の『システムデータ』が大きすぎる原因と減らし方」のような、あとで自分が見返す記録
  - **note は全記事がである・だ調**。「〜している」「〜だった」「〜と思う」「〜と思っている」「〜かもしれない」「〜だろう」で終わる文が中心
- 考えを書くときは、断定せずに **問いの形で終える** 文が多い。「〜のではないか。」「〜だろうか。」「〜のだろう。」。note では文末の 1 割以上がこの形
  - 例: 「では、どのように関わればよいのだろう。」「支援が少しずつ必要なくなっていくことが成功なのかもしれない。」
- 断定を避けるときの文末は「〜と思います」「〜と思っています」「〜と考えています」「〜ように感じました」「〜かもしれない」。「〜でしょう」は少ない。
- 「〜かな」「〜なぁ、と」「〜ですね」のような、口に出したままのような文末を、記事に 1〜3 回混ぜる。全部を整えすぎない。
  - 例: 「来月くらいから少しずつ時間を取っていくようにできればなぁ、と考えています」
- 感情は「楽しい」「面白い」「嬉しい」「煩わしい」のような平易な言葉で直接書く。「胸が熱くなる」「感慨深い」のような修飾はしない。
- 気持ちの揺れは **オノマトペ** で書く。「モヤモヤ」「ぐるぐる」「うずうず」「すいすい」「ふらりと」「チマチマと」。
  - 例: 「この一週間あたりで、自分は少しモヤモヤしている。」「まさに思考がぐるぐるしている状態だった。」
- 考えが整理できた瞬間は「しっくりきた」「アハ体験だった」「見え方が変わる」「だいぶ楽になった」と書く。
- 「！」はお知らせや感謝の場面で 1 記事に 1〜2 回まで。「笑」「w」は使わない（過去記事の「笑」は「笑い」の話題）。

## 3. 文と段落のリズム

- **Blog は 1 文 1 行**。文の途中で改行しない。文が終わったら改行する。段落は 1〜3 行で、空行で区切る。4 行以上続く段落はほとんどない。
- **note は段落の中に 2〜4 文を続ける**。1 文だけの段落は、言いたいことを際立たせるときに使う。
  - 例: 「前回は問題が起きてから対応した。今回は、できればその前に気づきたい。」の直後に 1 文だけの段落「自分は、チームを監視する人になろうとしていないだろうか。」
- 1 文は Blog で 40〜50 文字、note で 30〜40 文字が中心。長くても 80 文字程度。読点は 1 文に 0〜2 個。3 個以上入るなら文を分ける。
- 段落の先頭で話をつなぐ言葉は、次のものをよく使う。
  - 「今回は」「今回の」（記事の対象を示す）
  - 「そこで、」「ということで、」（行動に移る）
  - 「ですが、」「ただ、」「しかし、」（逆接）
  - 「実際に」「実際のところ」（やってみた結果）
  - 「また、」「あと、」（追加）
  - 「でも、」「ただ、」「一方で、」「もちろん、」「むしろ」「だったら、」（note の考えを進めるときの接続。「でも」を文頭に置くのは note の癖で、Blog ではあまり使わない）
  - 「そう考えると、」「そうなれば、」（考えの転換を受けて次へ進む）
- 「〜なので、」「〜ので、」で理由をつないでから結論を書く形が多い。「なぜなら」は使わない。
- 「〜という」「〜ということ」「〜ような」を使った、少し回りくどい説明を許容する。生成 AI 的に削ぎ落としすぎない。

## 4. 記事の型

記事は大きく 4 種類あり、それぞれ定型がある。

### 4.1 技術メモ（調べたこと、ハマったこと）

1. 冒頭に **`## TL;DR`** を置き、結論を箇条書きで 2〜4 点
2. `## 動機` または `## 経緯`（なぜそれをやる必要があったか。仕事や個人開発の具体的な状況から書く）
3. 本文（`## 実際のコード`「## やったこと」「## 使い方」など、事実の記述）
4. `## おわりに` または `## 参考`（参考にしたページのリンク一覧）

### 4.2 リリースのお知らせ（個人開発の gem、Chrome 拡張、npm など）

- タイトルは「**◯◯ vX.Y.Z をリリースしました**」
- 冒頭 1〜2 文で「何を作っているものか」と「リリースした」を書く。前置きの挨拶はない
- 変更点ごとに見出し。見出しに `:memo:` `:tada:` のような絵文字を付けることがある
- 各変更点に「経緯」を小見出しで添え、自分が困っていた具体的な状況を書く
- 末尾は定型の **`### 要望やバグ報告は GitHub まで`**。MIT ライセンスで公開していること、Issue から報告してほしいことを書く

### 4.3 イベント参加・登壇報告

- タイトルは「**◯◯に参加してきた**」「**◯◯で発表してきた。**」。末尾に `#ハッシュタグ` を付けることがある。句点で終わるタイトルも多い
- 冒頭は「◯月◯日に開催された [イベント名](URL) に参加してきました」と日付とリンクから始める
- 登壇なら Speaker Deck の埋め込みを冒頭近くに置く
- セッションごとの感想は見出しで分ける。運営や登壇者への感謝を素直に書く
- 末尾は `## 参考` または「次回も参加したい」で締める

### 4.4 近況（誕生日、転職、年末のふりかえり、寄付、資格）

- 年末のふりかえりは `## お仕事`（本業・副業）`## コミュニティ活動` `## 健康` / `## 筋トレ` `## 趣味` / `## 推し事` `## 次の目標` `## おわりに` の見出しで並べる
- 誕生日記事は「◯歳になりました。」がタイトル。末尾に「いつものアレ」として欲しい物リストへのリンク
- 転職などの報告は事実から書き始め、「今後とも宜しくお願いいたします。」で締める

### 4.5 共通

- `## はじめに` は基本使わない。前置きなしで本題に入る。2026 年の記事では使うことも出てきたが、使う場合も挨拶ではなく「何をした記事か」を 2〜3 文で書く
- 締めの見出しは **「おわりに」**。技術メモでは「まとめ」も使う（2026 年の記事では「まとめ」が多い）。「さいごに」「所感」は使わない
- 「おまけ」の見出しで本題からそれた小ネタを最後に付けることがある
- 記事あたりの見出しは 3〜5 個。細かく切りすぎない
- 記事の長さは 1,000〜2,500 文字。3,000 文字を超える記事はほとんどない

## 5. 語彙と表記

- 「色々」は漢字。「いろいろ」は使わない
- 「ふりかえり」はひらがな（「振り返り」は 2021 年以前のみ）
- 「下記」「以下」「こちら」でリンクや引用を指す。「下記のような」「以下のもの」「こちら：」
- 「ハマりどころ」「サクッと」「ちまちま」「雑に」「放置していた」のような、くだけた言い回しを技術記事にも使う
- 括弧は全角「（）」。半角括弧は英語の中だけ
- 会話や心の声は「」で書く。例: 「ここはこういう意味なのか」といった理解していくタイミングがありました
- 「」は、想像上の相手のセリフや自分への問いにも使う。note では 1 記事に 5〜10 回出る
  - 例: 「今日は何をするんですか」「問題はありませんか」と確認される側からすれば
  - 例: 一番しっくりきたのが「プロセスを育てる」という言葉だった
- 記事の核になる考えは、短い言葉に名前を付けて「」で囲み、末尾でもう一度使う。例: 「プロセスを育てる」「書く筋力」「驚き屋と飽きてきた屋」
- 「一旦」「なんとか」「わりきって」「ノリで」「雑に」「放置していた」のような、力の抜けた言い回しを許容する
- よく使う名詞: 学習、仕組み、プロセス、支援、問い、問いかけ、違和感、言語化、仮説、手戻り、フィードバック
- 英数字と日本語の間にスペースは入れない（textlint の設定どおり）
- 数字は半角。「1 年」ではなく「1年」

## 6. リンクと引用

- リンクのテキストは **ページのタイトルそのまま**。「こちら」だけをリンクにしない
  - 例: `[satoryu/copy-for-scrapbox: This is a Chrome extension which ...](https://github.com/...)`
  - 例: `[学習する／Unlearnするチームへ #RSGT2019 | TAKAKING22.com](https://...)`
- 外部サイトの紹介は `{% linkpreview "URL" %}` でカード表示する
- 本の紹介は表紙画像を Amazon へのリンクにして冒頭に置く
- 補足や言い訳は **脚注** `[^1]` に逃がす。本文の流れを止めない
  - 例: `[^2]: コミットはもっと細かくすればわかりやすくなったかもしれない、という反省。`
- 自分の過去記事や登壇資料への内部リンクを積極的に張る

## 7. 書かないこと

- 記事冒頭の挨拶や自己紹介（「こんにちは、◯◯です」）
- 「本記事では〜について解説します」のような予告文。書くなら「ここでは今回のリリース内容を紹介します」程度に短く
- 読者に売り込む結び。自分の仕事やサービスへの誘導で記事を締めない。書くなら本文の流れを止めない脚注か、短い一文に留める
- 「参考になれば幸いです」のような定型の締め。ただし、自分が作った OSS やツールの記事では「ぜひ試してみてください」「Issue を出していただけると大変よろこびます」のような軽い一言で締めることはある
- 見出しの番号付け、太字の多用、絵文字の多用（絵文字はリリース記事の見出しのみ）
- 「〜することで〜が可能になります」「〜を実現します」のようなプレスリリース調
- 表（テーブル）での比較。過去記事ではほぼ使っていない。使うなら箇条書き
- 一般論から入る導入（「近年、生成 AI の普及により〜」）。必ず自分の具体的な状況や出来事から始める
- 「〜すべきだ」「〜が重要だ」で終わる教訓。結論は「自分はこう試してみようと思っている」という自分の行動か、読者に投げる問いの形にする

## 8. フロントマター

```yaml
---
title: "タイトル"
category: blog
excerpt: |
  何をした記事か 1〜2 文。ですます調で「〜しました。」「〜を紹介します。」で終える。
tags:
  - タグ（既存のタグ名を優先して再利用する。例: Ruby, OSS, Chrome拡張, イベントレポート, 読書, Claude Code）
---
```

`header` は画像を使うときだけ付ける。`toc: true` は見出しが多い長めの記事のみ。

## 9. note の記事の型

note は「考えていること・仕事の進め方・読書・家族」を書く場で、技術の手順は書かない。Blog との役割の違いはトップページの案内にも書いてある。

### 9.1 毎日の短い記事（300〜1,300 文字）

- 見出しなし。2〜5 段落
- 1 文目でその日の出来事か状況を書く。「今日は〜」「最近、〜」「先日、〜」「〜して 1 か月が経過した」。前置きや一般論はない
  - 例: 「4 月から新しい 3 名体制のチームで働き始めて 1 か月が経過した。」「特にオチも何もない。」
- 出来事 → そこで感じた違和感や気づき → 誰かの言葉や本からもらった視点 → 自分がこれからどうするか、の順
- 末尾は「〜してみようと思う」「〜と考え始めている」「〜と願っている」のような、自分の次の行動や願い。読者への呼びかけはしない。短い一言で切ることもある（「ちょっとしたアハ体験だった。」「まだ離れきってはいないようだ。」）
- 本を挙げるときは Amazon の埋め込みを本文中に置く
- 家族（娘、息子）、読書と積ん読、推し、ゴールデン・ウィークのような生活の話題を、仕事の話と同じ調子で書く

### 9.2 長い記事（3,000〜4,700 文字、4 つの見出し）

- 見出しは 4 つで、それぞれが **文のような見出し**。名詞止めや「〜について」にしない
  - 例: 「問題を早く見つけたい。でも、報告会にはしたくない」「レビューをテストのように使う」「自分がいなくても改善できるチームへ」
- 流れは決まっている
  1. 具体的な状況（支援しているチーム、聞いた講演、慣れない仕事）を 2〜3 段落
  2. そこで生まれた不安や問い。「自分は〜になろうとしていないだろうか。」
  3. 見方を変えた瞬間。「〜として捉えてみると、かなり見え方が変わることに気づいた。」
  4. 具体的にどう関わるか。想定するセリフを「」で並べる
  5. うまくいった状態とは何か、これから試すこと
- 末尾は「この数か月は、それを自分なりに試してみようと思っている。」「〜のではないだろうか。」のように、意志か問いで終える
- 記事の核になる言葉を 1 つ決めて、見出しと末尾で繰り返す

### 9.3 タイトル

- 2 つの句を「。」でつなぐ形が多い。「生成 AI で実装が速くなった。その時間を何に使うのか」「思考がぐるぐる。堂々巡りはデバッグだった」
- 「A より、B」「A と B の間」のような対比。「問題を解決するより、プロセスを育てる」「驚きと飽きとの間」
- 問いの形でも「？」は付けない。「ソフトウェアを作った。その次の仕事は何だろう」
- 短い記事は、その日の結論をそのまま置く。「やっぱり Ruby を書きたい」「終わらないことを認める」「判断ポイントに仮定を一旦置く」
- ハッシュタグを 3〜5 個付ける（#生成AI #チームビルディング #読書 #ソフトウェアエンジニア など）
